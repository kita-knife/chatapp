# ChatApp-PG API

FastAPI backend that exposes multi-provider LLM chat via [agno](https://github.com/agno-agi/agno), with SSE streaming for assistant replies.

## Bootstrap (first time, from a clean machine)

These four commands take you from "PostgreSQL exists, code is cloned" to
"backend running with a usable root account":

```bash
# 1. Install Python deps (creates .venv/)
uv sync

# 2. Configure env (then edit LLM_API_KEY / WEB_BASE_URL / DATABASE_URL)
cp .env.example .env

# 3. Create the Postgres database (once per machine — pick your own name)
PGPASSWORD=postgreswsl psql -h localhost -p 5433 -U postgres \
  -c "CREATE DATABASE chatapp;"

# 4. After changing a model, generate a new revision (review the diff before committing):
uv run alembic revision --autogenerate -m "describe the change"

# 5. Apply schema migrations (creates ai schema + 5 tables + ai.alembic_version)
uv run alembic upgrade head

# 6. Bootstrap the first root user — REQUIRED before anyone can log in.
#    The web app has no self-signup flow; login will fail until this runs.
uv run python -m app.cli create-root --username root --password '<password>'

# 7. Start the dev server
uv run uvicorn app.main:app --reload --port 8000
```

Verify:

```bash
curl http://localhost:8000/api/health
# {"status":"ok"}
```

All tables (and `alembic_version`) live in the **`ai` PostgreSQL schema**,
not `public`. The DB connection URL is the same — only the table names are
qualified.

## Migrations

Schema is managed by [Alembic](https://alembic.sqlalchemy.org/) under the
`ai` PostgreSQL schema. The `api/migrations/` directory contains the full
history; the first revision (`0001_initial_schema`) was generated by
`alembic revision --autogenerate` from the SQLAlchemy models.

```bash
# Apply any pending migrations (run before first start, and on every deploy).
uv run alembic upgrade head

# After changing a model, generate a new revision (review the diff before committing):
uv run alembic revision --autogenerate -m "describe the change"

# Roll back the most recent migration (use sparingly on production):
uv run alembic downgrade -1

# Render the SQL Alembic would run without actually applying it (for review):
uv run alembic upgrade head --sql
```

The Docker image runs `alembic upgrade head` before starting uvicorn, and
Railway's `releaseCommand` does the same, so production deploys never start a
container against an outdated schema.

### Workflow for new migrations

1. Edit `app/modules/<area>/models.py`
2. `uv run alembic revision --autogenerate -m "short description"`
3. **Review** the generated file — autogenerate is good at column / index
   changes but misses: enum renames, table / column renames, default-value
   swaps, server-side default swaps, and any data backfill. Hand-edit
   when needed.
4. `uv run alembic upgrade head --sql` to dry-run the SQL
5. `uv run alembic upgrade head` to apply locally
6. Commit the new revision file alongside the model change

Do **not** regenerate revision `0001` — it is the bootstrap baseline; any
post-bootstrap schema change belongs in a NEW revision.

### Note on `version_table_schema`

`api/migrations/env.py` configures `version_table_schema="ai"`, which means
`alembic_version` lives in the `ai` schema alongside the business tables.

Alembic itself does NOT auto-create that schema — `env.py` issues a
`CREATE SCHEMA IF NOT EXISTS ai` before handing the connection to alembic,
so `alembic upgrade head` works on a brand-new empty database without any
manual bootstrap step. The same statement is repeated inside migration
`0001_initial_schema` so that offline `--sql` rendering also produces
correct DDL.

### Adopting Alembic on an existing database

If you previously let the app create tables via `Base.metadata.create_all`,
the schema already matches revision `0001`. Mark it as up-to-date without
re-running the DDL:

```bash
uv run alembic stamp head
```

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/health` | Health |
| `GET` | `/api/chat/models` | Models available in the UI |
| `POST` | `/api/chat/sessions` | Create session |
| `GET` | `/api/chat/sessions` | List sessions |
| `GET` | `/api/chat/sessions/{id}` | Get one session |
| `DELETE` | `/api/chat/sessions/{id}` | Delete session |
| `GET` | `/api/chat/sessions/{id}/messages` | List messages |
| `POST` | `/api/chat/sessions/{id}/messages` | Send a message — **response is SSE** |

### SSE event format

```text
data: {"delta": "你好", "finish_reason": null, "error": null}

data: {"delta": "", "finish_reason": "stop", "error": null}
```

## Provider routing

agno is used as the provider layer. The provider is selected by model prefix:

| Model prefix | Provider |
|---|---|
| `minimax*` | MiniMax OpenAI-compatible (default) |
| `gpt-*`, `o*`, `chatgpt-*` | OpenAI |
| `claude*` | Anthropic |
| `ollama:*`, `llama*`, `qwen*`, `mistral*` | Ollama (local) |

If the model doesn't match any prefix, the request falls back to the configured MiniMax endpoint.

## Config

See `.env.example` for the full template. The key variables are:

| Variable | Default | Description |
|---|---|---|
| `LLM_API_BASE` | `https://api.minimax.chat/v1` | OpenAI-compatible endpoint |
| `LLM_API_KEY` | _(empty)_ | API key for the endpoint above |
| `LLM_MODEL` | `MiniMax-M3` | Default model |
| `OPENAI_API_KEY` / `OPENAI_BASE_URL` | _(empty)_ | Optional OpenAI hook |
| `ANTHROPIC_API_KEY` | _(empty)_ | Optional Anthropic hook |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Optional Ollama hook |
| `POSTGRES_*` | `localhost:5433` / `chatapp` / `postgres` / `postgreswsl` | DB connection |
